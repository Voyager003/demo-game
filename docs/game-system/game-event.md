# 이벤트 시스템 (Event System)

## 1. 3레이어 이벤트 모델

### Layer 1. 결정론적 레이어 (Deterministic) — 비중 40%

> "하면 반드시 된다" — 학습 가능한 인과관계

| 행동 | 결과 |
|------|------|
| 복지비 증가 | 팀 케미↑, 충성도↑ |
| 연봉 인상 | 이직 확률↓ |
| 마케팅비 지출 | MAU 증가 |
| 리팩토링 완료 | 기술 부채↓ |
| PM 배치 | 딜레이↓, 재작업↓ |
| CTO 채용 | 개발팀 +10% |

**설계 원칙**: 플레이어가 "이건 하면 좋다"고 학습할 수 있어야 함

---

### Layer 2. 확률적 레이어 (Probabilistic) — 비중 35%

> "하면 될 수도 있다" — 조건 충족 시 확률 발동

| 조건 | 이벤트 | 확률 변화 |
|------|--------|-----------|
| 특성 충돌 | 팀 내 갈등 | 5% → 최대 40% |
| 체력 0 이하 | 번아웃 선언 | 3% → 35% |
| 충성도 0 이하 | 이직 통보 | 2% → 30%/턴 |
| 기술 부채 61+ | 서비스 장애 | 5% → 25%/턴 |
| 명성 70+ | 언론 기사 | 3% → 15%/턴 |
| 창업꿈나무 + 48턴 재직 | 퇴사+기술유출 | 0% → 60% |

**설계 원칙**: 0%와 100%는 존재하지 않음. 좋은 조건에서도 나쁜 일, 나쁜 조건에서도 버틸 수 있음

---

### Layer 3. 연쇄 효과 레이어 (Chain Reaction) —> 레이어 보다는 엔드포인트 

> "했는데 왜 이렇게 됐지?" — 반직관적 결과

#### 핵심 연쇄 시나리오

**시나리오 1: 마케팅 역풍**

마케팅 과투자 → MAU 급증 → 낮은 완성도에 유입 → 1성 리뷰 → 평점 급락 → MAU 순감소 → 투자사 신뢰↓ → 투자 실패

**시나리오 2: 복지 과잉의 역설**

복지비 과도 → 케미↑(단기 긍정) → 나태함 누적 → 생산성↓ → 딜레이 → 외주 만족도↓ → 명성↓ → 이력서 풀↓

**시나리오 3: 창업 꿈나무 해고의 부메랑**

해고 → 케미 소폭↓ → 경쟁사 창업(48턴 후) → 기술 유출 → 경쟁 서비스 MAU 역전 → 투자사 이탈

**시나리오 4: 스타 개발자 딜레마**

연봉 인상 거절 → 이직 → 급한 후임 채용 → 낮은 명성으로 하급 인재 → 팀 스탯 하락 → 프로젝트 티어 강등 → 외주 수입 감소

### 연쇄 설계 원칙

- 최소 3단계 이상 거쳐야 반직관적 결과 도달
- 중간 단계에서 개입 가능한 선택지 제공
- 긍정→부정 연쇄와 부정→긍정 연쇄를 함께 설계

## 2. 특성 공개 메커니즘

히든 특성은 확률 기반이 아닌 **구조적 공개 시스템**을 따른다. 채용 후 시간이 경과하면서 단계적으로 공개된다.

```
정규직:
  이력서: 1~2개 확실 공개 + 나머지 힌트
  수습 4턴: 카테고리 힌트 공개
  수습 8턴: 구체적 힌트 공개
  수습 12턴 (전환 전): 모든 특성 완전 공개

계약직/외주: 8턴 이내 전체 공개
```

상세는 [특성](../game-domain/trait.md)의 "특성 공개 시스템" 참조.

## 3. 외부 환경 이벤트

- **시장 트렌드**: 매 20~30턴마다 1개 발생
- **법규제**: 조건 충족 시 발동
- 상세 목록 → [이벤트 카탈로그](../game-domain/event-catalog.md) 참조

## 4. 이벤트 발생 타이밍

- 게임 진행의 **Phase 1 (Event Phase)**에서 판정
- **긴급 이벤트**는 피로도를 소모하여 즉시 대응 (예: 긴급 장애 대응 피로도 3)
- **비긴급 이벤트**는 Phase 2 (Decision Phase)에서 대응

---

## 5. 레이어 간 상호작용

```
결정론적 레이어 (토대)
       ↓ 조건을 형성
확률적 레이어 (긴장감)
       ↓ 이벤트를 발생
연쇄 효과 레이어 (반전)
       ↓ 예상 밖 결과
플레이어의 다음 의사결정
```

---

## 6. 이벤트 레이어 로그 시스템

모든 발생 이벤트는 **어떤 레이어에서 트리거되었는지** 기록된다. 플레이어는 이 로그를 통해 이벤트의 인과관계를 학습할 수 있다.

### 로그 항목

| 필드 | 설명 |
|------|------|
| **턴 번호** | 이벤트 발생 턴 |
| **이벤트명** | 발생한 이벤트 이름 |
| **트리거 레이어** | 결정론적 / 확률적 / 연쇄 효과 |
| **트리거 조건** | 이벤트 발생 원인 요약 (예: "기술 부채 65 → 서비스 장애 확률 발동") |
| **결과** | 이벤트 결과 요약 |

### 로그 접근

- **Phase 5 (결과 보고)**: 해당 턴 발생 이벤트의 레이어를 색상으로 구분 표시
- **이벤트 로그 확인** (무료 행동): 전체 히스토리 열람 가능
- **연쇄 효과 이벤트**: 선행 이벤트 체인을 펼쳐볼 수 있음

### 레이어 색상 구분

| 레이어 | 색상 | 의미 |
|--------|------|------|
| 결정론적 (Deterministic) | 파랑 | "하면 반드시 된다" |
| 확률적 (Probabilistic) | 노랑 | "하면 될 수도 있다" |
| 연쇄 효과 (Chain Reaction) | 빨강 | "했는데 왜 이렇게 됐지?" |

> 레이어 로그는 플레이어가 "왜 이 이벤트가 발생했는지"를 이해하고, 다음 플레이에서 더 나은 의사결정을 내리도록 돕는다.
