# 기술 (Tech)

---

## 기술 부채 (TechDebt)

- **범위**: 0~100
- IT 시뮬레이션의 핵심 요소: 빠른 납품과 안정성 사이의 딜레마

### 구간별 효과

| 구간 | 효과 |
|------|------|
| 0~20 (Green) | 정상 — 패널티 없음 |
| 21~40 (Yellow) | 버그 발생 확률 +10% |
| 41~60 (Orange) | 신규 기능 개발 속도 -15%, 버그 확률 +25%, **모든 작업 +1턴 소요** |
| 61~80 (Red) | 장애 이벤트 발생 확률↑, 신규 개발자 투입 효율 -20%, **모든 작업 +1턴 소요** |
| 81~100 (Critical) | 리팩토링 강제 발생, 신규 개발 중단 |

> **+1턴 패널티**: 기술 부채 41 이상에서 활성화. 예정 소요 5턴인 작업이 6턴으로 늘어난다.

### 서비스형 성장 지표 영향

기술 부채는 주수입원 프로젝트의 서비스형 성장 지표에 직접 영향을 미친다.

| 구간 | 서비스 영향 |
|------|-----------|
| 0~20 | 없음 |
| 21~40 | 서비스 안정성(Stability) 소폭 감소 |
| 41~60 | 서비스 평점(Rating) 하락 확률 +15%, 버그 발생으로 인한 이용자 이탈 +5% |
| 61~80 | 서비스 평점 하락 확률 +30%, 장애 이벤트로 인한 이용자 이탈 +10% |
| 81~100 | 서비스 운영 불가 수준. 신규 기능 개발 중단, 긴급 리팩토링 필수 |

### 누적 조건

| 조건 | 부채 증가량 |
|------|-----------|
| **개발자 수 × 시간 경과** (자연 증가) | +1/개발자/4턴 |
| 납기 단축 선택 | +5~+15/프로젝트 |
| 속도제일주의 특성 투입 | +3/프로젝트 |
| 야근 연속 3턴 이상 | +2/턴 |
| 코드리뷰 없이 배포 | +5/배포 |
| 리팩토링 완료 | -20~-40 |

> **자연 증가**: 개발자가 많을수록, 시간이 지날수록 기술 부채는 자연스럽게 누적된다. 개발자 3명이면 4턴마다 +3씩 증가. 이는 코드베이스가 커지면서 발생하는 현실적 복잡도를 반영한다.

## 리팩토링 프로젝트 (Refactoring)

- **착수 조건**: 플레이어 자발적 or 기술 부채 81+ 시 강제
- **소요 턴**: 4~12턴 (팀 규모 및 부채 수준에 따라)
- **비용**: **수익 활동 전면 불가**. 리팩토링 기간 동안 외주 수주 불가, 주수입원 프로젝트의 서비스형 확장 개발 중단. 인건비 및 운영비는 계속 발생하므로 재무 계획 수립이 필수.
- **효과**: 기술 부채 -20~-40, 이후 생산성 +10%
- **리팩토링 중 제약**: 신규 기능 개발 불가 (유지보수만 가능)

> **전략적 딜레마**: 리팩토링은 장기적으로 필수이지만, 단기적으로 수입이 끊기는 고통이 따른다. 런웨이가 충분할 때 선제적으로 실행하는 것이 최선이나, 현실적으로는 부채가 임계점에 도달한 후에야 착수하게 되는 경우가 많다.
